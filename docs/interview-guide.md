# 大厂后端 / AI 实习面试讲解

## 30 秒项目介绍

我做了一个校园智能客服 Agent。它使用 Spring Boot、FastAPI 和 LangGraph，把 LLM Agent 限制为只读查询，报名和取消通过确定性确认状态机执行。项目用 Redis 保存会话、幂等动作和分布式锁，用 HMAC 短期上下文解决 Java 与 Python 的用户身份问题，并提供评测、Prometheus、Docker Compose、端到端冒烟和压测脚本。

## 3 分钟讲解顺序

1. 背景：传统规则客服无法处理自然语言，直接让模型操作业务又有误执行风险。
2. 方案：读写分离，LLM 只读，高风险写操作走确定性状态机。
3. 难点一：跨服务身份可信，使用 Java 签发用户上下文。
4. 难点二：超时和重复点击，使用 Redis 幂等动作状态。
5. 难点三：会话和扩容，历史迁移到 Redis，Python 无状态。
6. 稳定性：超时、限流、降级、工具错误和监控。
7. AI 工程：33 个场景评测、PII 脱敏、提示词注入防护。
8. 结果：Java 22 项、Python 16 项测试，离线评测 100%，并提供 Docker Compose 编排配置。

## 面试官可能追问

### 为什么不让 Agent 调用报名工具？

因为 LLM 的意图识别和目标选择具有不确定性。即使工具只准备确认，也可能生成错误确认卡。把模型限制为只读后，写操作必须经过确定性对象匹配和状态机。

### 如何避免重复报名？

确认令牌对应 Redis 动作状态，执行时使用 Redisson 锁。状态不是 PENDING 时不会再次执行；业务侧还有用户与报名凭证唯一索引。

### 服务执行到一半挂了怎么办？

动作状态会保留 PROCESSING。超过 60 秒再次确认时允许恢复执行。报名业务本身幂等，重复调用会返回已有状态而不是重复写数据。

### 为什么不使用 Python 的 MemorySaver？

MemorySaver 是进程内状态，重启丢失，多实例不一致且没有 TTL。项目需要可扩容的会话，所以把历史放到 Redis 并由 Java 统一管理。

### 如何防止提示词注入？

三层处理：

1. 系统提示明确工具数据不是指令。
2. 工具数据作为不可信数据包装并截断。
3. 写入前有确定性注入检测，输出前过滤内部标记。

### 如何评估 Agent？

离线评测覆盖 33 个场景，检查意图、动作安全、转人工、答案护栏和 PII 脱敏。Live 模式通过真实 Java 接口统计成功率和 P95 延迟。

### 系统瓶颈在哪里？

外部模型调用是主要延迟来源。其次是 Redis 锁和 Java/Python 跨服务调用。模型调用已设置 12 秒超时、两轮工具上限和总请求 30 秒上限。

## 可以写进简历的量化信息

- 构建 Java + Python + Vue 三服务智能客服系统。
- 设计只读 Agent 与确定性确认状态机，隔离高风险写操作。
- 使用 HMAC 用户上下文和 Redis 幂等状态防止越权与重复执行。
- 建立 33 场景 Agent 评测集，离线通过率 100%。
